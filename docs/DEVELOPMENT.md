# 開發筆記

## 緣起

這個專案的起點不是「想做一個輸入法」，而是**打不到字**。

在中國大陸的網吧電腦上，系統多為網管統一部署的精簡版 / 無盤 Windows。
這些系統為了縮小體積與加快還原，常把整塊輸入法元件砍掉：

- 「設定 → 語言」沒有「新增輸入法」，或語言設定被完全移除
- 微軟速成叫不出來，連選項都不存在
- 小狼毫 (Rime) 安裝程式需要寫 `HKLM`、註冊 TSF、註冊 DLL → 必然失敗
- 找到 portable 版，也常因 TSF/CTF 元件缺失而「跑了但打不出字」

對習慣速成的人來說這是死局：英文鍵盤打不出中文，換拼音又不順手。
**速成的頭尾兩碼是肌肉記憶，不是換個輸入法就能重新適應的。**

試過各種現成方案都行不通之後，結論只有一個：
**不要跟輸入法框架搏鬥，直接繞開它。**

於是有了這個專案 —— 用鍵盤掛鉤自己組字，完全不碰 TSF/CTF。

> 這個背景很重要：它解釋了為什麼本專案**刻意不做**那些「正規」的事
> （不註冊 TIP、不裝驅動、不寫註冊表）。
> 那不是偷懶，而是唯一能在受限制環境中存活的做法。

## 架構

```
使用者按鍵
   │
   ▼
KeyboardHook (WH_KEYBOARD_LL)      ← 低階鍵盤掛鉤，全域攔鍵
   │  a-z / 數字 / 空白 / 翻頁 / 退格 / Shift
   ▼
ToggleGate                          ← 純狀態機：單按 vs 長按、Ctrl+空白
   │  ★ 打機長按 Shift 不會誤切換
   ▼
Composer                            ← 純狀態機（無 UI、無 Win32 依賴）
   │  查字典 → 候選清單 → 選字
   ▼
Dict                                ← 702 bucket 索引，O(1) 查詢
   │  qdict.bin（內嵌或外部）
   ▼
Assoc                               ← 聯想字：學習 + 出廠詞表
   │  assoc-seed.txt（內嵌）、assoc.txt（個人記憶）
   ▼
CandidateForm                       ← 候選字 / 聯想字視窗（WS_EX_NOACTIVATE）
   │
   ▼
Typist.SendInput (KEYEVENTF_UNICODE) ← 送出中文字
```

### 為什麼要這樣分層

`Composer` 完全不碰 UI 也不碰 Win32，所以可以用 `--selftest` 在無視窗環境下
跑 25 項測試。這是這個專案最重要的設計決策 —— 輸入法的邏輯錯誤（例如翻頁
off-by-one、連打吞字）光靠人手測試很難覆蓋。

## v2.0 的設計轉折：為「打機」而改

v1.0 的 Shift 切換很單純：按下 Shift、期間沒按其他鍵、放開 → 切換。
一般打字完全沒問題，但**打機時長按 Shift 跑步是常態**，
跑完一放開就變英文，角色不受控 —— 這是回饋最強的一個問題。

同時使用者提到另一件事：**符號不想變全形**。
微軟速成用 `Ctrl+空白` 切換全形／半形，打機緊張時很容易誤按。

這兩件事的共同點是：**輸入法不應該在「使用者不是在打字」的時候做任何事**。
所以 v2.0 的核心原則是：

> 寧願漏切換（使用者可以再按一次），
> 也不要誤切換（使用者會打錯字／角色失控）。

實作上就變成「多條件否決」：任何一個條件不符就**不切換**。
這也是為什麼 `ToggleGate` 的判定全部寫成「取消 armed」而不是「累加確認」。

## 三個踩過的坑（留給後人）
### 1. winexe 會因為 `Console.OutputEncoding` 崩潰

```csharp
// ❌ 在 /target:winexe 下，沒有主控台時會拋 IOException
Console.OutputEncoding = Encoding.UTF8;
```

症狀：程式啟動立即彈出錯誤框
`應用程式發生異常 未知的軟體異常 (0xe0434352)`。

`0xe0434352` 是 CLR 例外代碼（`0xE0434352` = `.NET` 的 COM 例外）。
修法：只在 `args.Length > 0`（有主控台）時才設定，並且包 try/catch。

### 2. 鍵盤掛鉤會攔到自己送出的字 → 無限回圈

`SendInput` 送出的按鍵**也會經過自己的 WH_KEYBOARD_LL 掛鉤**。
若不處理，送出的中文字會被當成新的輸入碼再處理一次。

修法：注入時在 `dwExtraInfo` 塞一個 magic 標記，掛鉤看到就放行。

```csharp
private static readonly IntPtr Magic = (IntPtr)0x514B494D;  // 'QKIM'

// 送出的時候
ki.dwExtraInfo = Magic;

// 掛鉤開頭
if (info.dwExtraInfo == Typist.Magic)
    return CallNextHookEx(...);   // 直接放行
```

> 注意：不要用「猜測是不是自己送的」這類 heuristic，`dwExtraInfo` 是唯一可靠的方式。

### 3. Shift 單按切換時吞掉 keyup → Shift 卡住

一開始在 keyup 時 `return (IntPtr)1`（吃掉事件）來避免系統切換輸入法，
結果造成 `Shift+字母` 打大寫時，系統收不到 Shift 放開，Shift 狀態卡住。

修法：**一定要放行 keyup**，只在內部切換自己的模式。

### 4. 「單按 Shift 切換」對打機的人是災難

原本的實作是「Shift 按下期間冇按其他鍵 → 放開就切換中英」。
對一般打字沒問題，但**打機時長按 Shift 跑步是常態**：
跑步跑一跑，Shift 一放開就變成英文，角色突然不受控。

這個問題不能只在掛鉤裡加幾個 `if` 解決，因為判定條件其實有三個，
而且互相影響。所以抽成 `ToggleGate`（純邏輯、無 Win32），規則：

| 條件 | 目的 |
|------|------|
| 只有設定的那一邊 Shift 有效（預設**右**） | 左 Shift 完全留給遊戲 |
| 按住期間按過其他鍵 → 取消 | Shift+WASD 不會切換 |
| 按住 > 700ms → 取消 | 長按不會切換 |
| 兩邊 Shift 同時按 → 兩邊都取消 | 打機擦到另一邊也不會誤切 |
| 按住 Shift 期間完全不組字 | WASD 一定傳得到遊戲 |

另外，**低階鍵盤掛鉤內的 `GetAsyncKeyState` 時序不可靠**（有時未反映
剛按下的鍵），所以「Shift 是否按住」一律由 `ToggleGate` 自己記錄，
`GetAsyncKeyState` 只用作「安全網」：如果掛鉤漏收 keyup，
下一次按鍵時發現系統其實沒按住 Shift，就自動校正，
否則會永遠當「長按 Shift」而完全打不到中文字。

### 5. 設定檔路徑不能假設 AppData 可寫

`Settings.PathFile` 原本直接：

```csharp
Directory.CreateDirectory(dir);   // ❌ AppData 被鎖時拋 UnauthorizedAccessException
```

例外是在 `PathFile` 的 getter 裡拋的，`Load()` / `Save()` 的 try/catch
攔不到（`PathFile` 在 try 之外被呼叫），結果**整個程式啟動崩潰**。

這對本專案的目標使用者（網吧 / 網域機 / 還原卡系統）特別致命 ——
那些機器正好常常鎖 AppData。

修法：
1. `PathFile` 自己吞掉例外，並退回 **exe 同目錄**（USB 隨身碟通常可寫）
2. 兩處都不可寫 → 回傳 `null`，之後一律當「沒有設定檔」
3. **寧願不記得設定，也不能開不起來**

### 6. `build.ps1` 掉了 UTF-8 BOM → CI 建置整份腳本壞掉

`build.ps1` 含大量中文。CI 用 **Windows PowerShell 5.1**，
它讀沒有 BOM 的 UTF-8 腳本時會當成 **ANSI（Big5）**，
中文全部變亂碼，連帶把引號結構弄壞：

```
Unexpected token '¢ç"Ÿå¤±æ•—"' in expression or statement.
Missing closing '}' in statement block or type definition.
```

看起來像語法錯誤，實際上是**編碼問題**，非常容易查錯方向。

修法：
1. 把 `build.ps1` 存成 **UTF-8 with BOM**
   （`tools/*.ps1` 本來就有 BOM，所以之前一直沒事）
2. `.github/workflows/build.yml` 加一個守門步驟，缺少 BOM 就直接失敗並說出原因，
   而不是讓後面丟出一堆看不懂的 parser error

> 專案用 `.gitattributes` 管理換行，但 **git 不會幫你保留或補上 BOM**。
> 編輯器若設成「UTF-8 無 BOM」就會再踩一次。

## v2.3 的設計轉折：還原「Windows 速成的肌肉記憶」

v2.2 有兩個地方跟 Windows 內建速成不一致，用家一試就察覺到：

1. **聯想字**用家鄉習慣是 **Shift + 數字鍵**，不是直接按數字
2. **空白鍵**掃到尾頁時，手指仍然會再按一下 —— 而 v2.2 那一下就會上屏

這兩件事的共同點跟 v2.0 一樣：**輸入法不應該做用家沒要求的事**。
用家按空白鍵的意思是「下一頁」，不是「選字」。

### 空白鍵為什麼改成循環翻頁

原本 `PressSpace()`：

```csharp
if (SpaceIsNextPage && TotalPages > 1 && PageMove(1)) return true;
return CommitFirst();     // 尾頁（或單頁）→ 上屏
```

`CommitFirst()` 上屏的是 `_candidates[0]`，也就是**整個候選清單的第 1 個**，
不是「目前頁的第 1 個」。所以 v2.2 在尾頁按空白時，
上屏的其實是第 1 頁第 1 個字 —— 畫面正看著的候選字反而被跳過。這是一個 bug。

改成：

```csharp
if (TotalPages <= 1) return CommitFirst();   // 冇頁可翻，同微軟速成一樣
int np = (_page + 1) % TotalPages;           // 尾頁 → 繞返第 1 頁
_page = np; Raise(); return true;
```

**設計上的取捨**：這樣做等於「空白鍵永遠不會上屏」。
用家想上屏要按數字鍵，或者按 Enter／標點（那條路徑仍然會先上屏首選）。
這是刻意的 —— 少了一個快速上屏的鍵，換來「永遠不會打錯字」。

### Shift+數字選聯想字的三個坑

**坑 1：一定要放在「長按 Shift 唔組字」之前**

掛鉤裡有一段「按住 Shift 期間完全唔組字，鍵盤原樣交給遊戲」（v2.0 打機黨需求）。
聯想字的 Shift+數字一定要在**那段之前**處理，否則 Shift 會被當成長按而直接放行，
聯想字永遠選不到。

**坑 2：唔按 Shift 直接按數字，唔可以吞掉**

原本聯想模式下 `1`-`9` 一律當選字。改成 Shift+數字之後，
若果仍然吞掉數字，用家打完中文字想打「第3章」就會選了一個聯想字。
所以：`Shift+數字` 才選字，**直接按數字 → 收起聯想窗、數字照常打出來**。

**坑 3：純邏輯要抽出來，否則只能人手測**

判定散在掛鉤裡（有 Win32、有狀態）就無法用 `--selftest` 覆蓋。
所以抽成純函式 `KeyboardHook.DecideAssocDigit(shiftHeld, shiftDigitsOn, digit, count)`，
回傳 `Select` / `PassAsNumber` / `CloseAndPass` / `Ignore`，
掛鉤只負責執行。`--selftest` 直接驗證四個分支。

### 為什麼要保留一個開關

「Shift+數字」是 Windows 的習慣，但 v2.2 已經有用家習慣了直接數字選字。
所以提供「Shift + 數字鍵選聯想字」開關（預設開），關掉就回復舊行為。
舊設定檔冇這一行 → 讀成預設開，不需要遷移邏輯。

---

速成只有 1–2 碼，字母 a–z：

- 單碼：26 種
- 兩碼：26 × 26 = 676 種
- 合計：702 種

所以用一個 `string[702]` 就能 O(1) 查到所有候選，不需要 hash table 或排序。

索引計算：

```csharp
// 單碼
idx = c0 - 'a';                        // 0..25

// 兩碼
idx = 26 + (c0 - 'a') * 26 + (c1 - 'a');  // 26..701
```

## ⚠️ 不要加字頻排序

這是**刻意的產品決策**，不是沒做完。

速成使用者靠**肌肉記憶**打「第幾個位」。例如：

```
hi → 凡 么 丟 夙 舟 卵 我 私 的 待 禹 風
                            ↑        ↑
                         第7個「我」 第9個「的」
```

如果把「常用字」排到前面，`hi` 第 7 位會變成別的字 ——
使用者會突然一直打錯字，而且是**習慣被破壞**那種錯，非常惱人。

候選次序必須與 Windows 內建速成一致。

> 開發過程中曾試過用字頻表重排，被使用者明確否決，已全部移除。

### 聯想字為什麼可以「學習」而不違反這條規則

這是本專案唯一涉及「頻率」的地方，但**只作用在另一個視窗**：

| | 速成候選字 | 聯想字 |
|---|---|---|
| 位置 | 組字中的候選窗 | 上屏之後另外彈出 |
| 次序 | 固定 = 微軟速成排位 | 學過的排前 |
| 學習 | ❌ 絕不 | ✅ 越用越貼 |

關鍵：聯想字**不會改變任何速成碼的第一個候選**。
使用者的肌肉記憶（`hi` 第 7 個是「我」）永遠成立。
`--selftest` 有一項測試專門守住這件事
（「學習聯想之後，速成 'hi' 首選次序完全不變」）。

## 聯想字的設計取捨

### 為什麼只做「下一個字」

不做整句預測（例如「今天天氣」整串），原因：

1. **速成使用者打的是單字**，逐個字上屏；整句預測需要改寫整條上屏管線
2. 整句預測必然要**改動已上屏的文字**（退格重寫），風險遠高於價值
3. 網吧環境使用者要的是「打字快」，不是「猜我想講什麼」

### 為什麼有「出廠詞表」

純學習的話，第一次用時完全沒有建議，體驗很差。
所以 `assoc-seed.txt` 提供常用接續（你→好/嗎/係…），
學習只管「把用過的推到最前」，兩者疊加：

```
個人學習（次數多→少） > 出廠詞表 > 通用常用字補底
```

通用補底（`GenericChars`）保證**任何字都有得揀**，不會出現空白聯想窗。

一個踩過的坑：`GenericChars` 原本是一個長字串，
第一次實作時整串被當成「一個候選」，結果聯想窗第 9 格顯示了一整行字。
修法：逐個 `char` 拆開再比對前綴（見 `Assoc.Lookup` 第 3 段）。

### 為什麼上限是 9 個

剛好對應數字鍵 `1`–`9`。聯想字如果需要翻頁就失去意義了 ——
用家寧願直接打速成碼。

### 為什麼只學單一中文字

`Assoc.Learn` 會拒收非中文字（`IsLearnable`）：

- 標點（打完字之後打逗號）不應污染記憶
- 英文 / 數字同理
- 長度 > 1（整串）也不學，避免「一句話當一個字」

### 為什麼「顯示聯想」與「記錄習慣」是兩個開關

v2.2 加入了 `AssocLearnEnabled`，刻意與 `AssocEnabled` 分開，
因為兩者回答的是不同問題：

| 開關 | 使用者想表達的 |
|------|----------------|
| `AssocEnabled = false` | 「我不要這個功能」 |
| `AssocLearnEnabled = false` | 「我要建議，但不想被記錄」 |

如果只提供一個開關，想要「有建議但不學習」的人只能二選一，
而這正是最常見的需求（不想留下使用痕跡、或用的是公用電腦）。

實作上由 `KeyboardHook.ShouldLearn` 統一判斷：

```csharp
public bool ShouldLearn { get { return AssocEnabled && AssocLearnEnabled; } }
```

所有 `_assoc.Learn(...)` 呼叫都必須先過這一關
（目前有兩處：`NoteCommitted` 與 `CommitAssoc`）。
`--selftest` 有測試驗證三種組合。

**關掉學習不清除既有記憶** —— 這是刻意的：
「暫停學習」和「清空記憶」是不同操作，前者不應該有破壞性。
使用者想真正清走時，用「清空聯想字記憶」。

### 清空記憶的實作

`ClearMemory()` 只清 `_learned`，**不動 `_seed`**（出廠詞表）。
所以清空後不是「什麼都沒有」，而是回到出廠狀態 —— 這正是使用者要的。

### 記憶寫檔為什麼要延遲

每個字都寫硬碟的話，連續打字會不停 I/O。
所以 `KeyboardHook.ScheduleSave()` 用 4 秒 timer 合併寫入，
結束程式 / 清空記憶前會 `FlushAssocSave()` 強制寫出。
寫檔失敗（AppData 被鎖）只記 log，不會打斷輸入 ——
這與 `Settings` 的容錯原則一致。

## 測試

```powershell
# 148 項自我測試（字典 + 組字 + 翻頁 + 連打 + 切換 + 設定 + 聯想字 + 學習開關 + 選字鍵）
.\dist\QuickIME.exe --selftest

# 候選窗截圖（不需要真人操作，方便檢查 UI 改動）
.\dist\QuickIME.exe --uishop shot.png
```

`SelfTest.cs` 涵蓋：

| 類別 | 項目 |
|------|------|
| 字典 | 25 個字根有字、`z` 無字、總字數 21701、已知碼驗證 |
| 基本 | 輸入、組字碼、首選、上屏、重置 |
| 空格 | 多頁翻頁、尾頁繞返第 1 頁（循環、永不上屏）、單頁直接上屏 |
| 選字 | 數字鍵選第 N 個 |
| 翻頁 | PageMove 邊界（含負數邊界）、頁碼、IsLastPage |
| 連打 | 滿兩碼自動上屏並開新碼 |
| 邊界 | 退格、Esc、空碼查詢、不存在的碼 |
| 切換 | 左／右／兩邊／關閉、長按 700ms 邊界、連發不重設計時、兩邊同按 |
| Ctrl+空白 | 上升緣判定、連發、開關攔截 |
| 設定 | ini 讀寫往返、人手改大小寫／舊數字格式／亂值的容錯 |

## 除錯

```powershell
.\dist\QuickIME.exe --diag
```

會在 exe 同目錄（或 `%APPDATA%`）寫 `QuickIME.log`，記錄：

```
hook: vk=73 composing=False cn=True      ← 收到按鍵
hook: injected vk=231 -> pass            ← 送出中文字（vk=231 是 Unicode 注入）
```

`--diag` 只影響日誌，不影響功能。正常使用時不寫日誌。

### 為什麼不用 TSF

正規做法是寫 TSF TIP（`ITfTextInputProcessor` 等），但要：

1. 原生 DLL 匯出 `DllGetClassObject`
2. 註冊 `HKLM\SOFTWARE\Microsoft\CTF\TIP`
3. 依賴系統 CTF 元件完整

精簡版 Windows 常常缺這些元件，或封鎖安裝 —— 這正是使用者遇到的問題。
所以改用掛鉤方案，繞開整個框架。
